###  1.1. Назначение системы.
...Приложение НКП является инструментом электронного голосования, учёта волеизъявления граждан и цифровой идентификации. 
...Оно не является банком, платёжной организацией или финансовым учреждением. 
1. Приложение НКП является инструментом электронного голосования,    учёта волеизъявления граждан и цифровой идентификации.
2. Оно не является банком, платёжной организацией или финансовым учреждением.
3. Касса не является объектом голосования, но является общенародной  собственностью и объектом контроля НКП.
   (Кассиры не голосуют из модуля кассы. Функция НКП в кассе — проверка    подлинности подписей ответственных лиц, дающих распоряжения на    проведение транзакций, и обеспечение прозрачного аудита)

## 1.7  Два режима обработки и хранения информации
- Система поддерживает два режима хранения и синхронизации данных:
-   1. Режим P2P (ПК-Хранители)
- - Данные хранятся децентрализованно на ПК-Хранителях пользователей.
- Синхронизация через протоколы libp2p и P2P-сеть.
- Основной режим для Этапа 1 (до 10 000 пользователей).
-  2. Режим Дата-центров
- Данные хранятся на профессиональных серверах (дата-центрах) при масштабировании
свыше 20 000+ пользователей. 
-   Синхронизация через защищённые каналы.
-  3. Переход между режимами:
- Бесшовный и плавный: Данные не теряются, синхронизация продолжается без 
вмешательства пользователя. Система автоматически определяет, какой режим 
активен, и переключается при необходимости (например, при 
выходе из строя ПК-Хранителей).
-   Криптографическая защита (хеши, МК, TOTP) сохраняется в обоих режимах.
## 1.7.1 Фиксация времени (Source of Truth).
- Система фиксирует момент начала голосования и далее ведёт отсчёт времени локально. 
- При подключении к сети  производится корректировка времени по узлам синхронизации.
    • «Временем истины (Source of Truth) для всех блокировок и разрешений является 
    системное время ПК-Хранителя, 
    синхронизированное по NTP.
    • Время на мобильном устройстве пользователя игнорируется и используется 
    исключительно для отображения на экране».
    • Система привязана к локальному времени региона, к которому привязан 
    пользователь и его Хранитель.
    • Для каждого голоса сохраняется неизменяемая временная метка (Timestamp) 
    момента его регистрации, которую 
    невозможно отредактировать задним числом.
## 1.8  Взаимодействие с "Кассой" (Внешний модуль).
- Финансовый модуль "Касса" является отдельным, независимым юридическим и 
программным контуром. "Касса" не имеет  права проводить транзакции без 
подтверждения личности через НКП. НКП выполняет для "Кассы" только функцию 
идентификации и не участвует в движении денежных средств.
##  1.9  Внешние сервисы.
- Передача данных во внешние сервисы (Google Диск, Telegram и др.) возможна 
только по явной команде пользователя для его личных целей. 
Эти сервисы не являются частью архитектуры хранения НКП.

## 2.0.1 Шардированная архитектура реестра.
- Для обеспечения быстродействия и хранения данных 50+ млн аккаунтов используется шардированная архитектура. Реестр данных сегментирован на независимые шарды. Каждый шард может размещаться на узлах ПК-Хранителях (автономные сервера на ПК) и обслуживает определённый сегмент пользователей. Синхронизация между шардами осуществляется по протоколу P2P/MESH. 
- Узлы сети могут разворачиваться любым участником сообщества на добровольной основе. Система не использует технологию блокчейн.
- Каждый шард хранит зашифрованные данные только тех пользователей, которые закреплены за данным ПК-Хранителем. Это исключает возможность подмены данных через взлом одного узла. Никакой человек не решает, кто куда попадёт. Только математика - алгоритмы распределения.

## 2.1.Автоматическое перераспределение нагрузки:
    • Система вычисляет нагрузку на каждый ПК-Хранитель и равномерно распределяет шарды между всеми активными узлами.
    • При выходе из строя одного Хранителя (нет ответа более 72 часов), его шарды автоматически перераспределяются
     между оставшимися узлами.
    • При добавлении нового Хранителя система перераспределяет часть шардов с самых загруженных узлов на новый, чтобы
     нагрузка оставалась равномерной.
    • Никакого ручного вмешательства. Всё происходит автоматически, на основе алгоритмов распределения.

## 2.2.  Разделение ролей устройств.

    • На смартфонах блокируется серверная часть (шард-движок).

## 2.3. Функциональные требования к ПТ.
- 2.3.1  Программное обеспечение ПТ
    • На ПТ устанавливается облегчённая версия приложения НКП — Режим «Токен» (Модуль ПТ).

## Управление камерой в Модуле ПТ 
- Рекомендуемая платформа
Для ПТ рекомендуется использовать телефоны на KaiOS, так как они предоставляют прямую и документированную поддержку камеры через API navigator.b2g.cameras.   
- Процесс использования камеры:
-  1. Запрос разрешения: Приложение запрашивает у пользователя разрешение на использование системной камеры
- (android.permission.CAMERA).
-  2. Получение доступа: После получения разрешения приложение получает доступ к системной камере через API 
-   (например, navigator.b2g.cameras для KaiOS).
-   3. Отображение видоискателя: Приложение самостоятельно отображает изображение с камеры (видоискателем)     в своём интерфейсе.
-   4. Съёмка: Когда пользователь нажимает кнопку «Сделать снимок», кадр захватывается кодом приложения      (например, через метод getSnapshot()).
-   5. Обработка и удаление: Полученное изображение обрабатывается (сверяется с бумажной копией) и немедленно     удаляется из памяти устройства при отключении камеры.  Фотографии не сохраняются.
- Важно: Управление камерой происходит исключительно внутри приложения. Внешние приложения и сама операционная 
система не вмешиваются в процесс.
## 2.3.5  Реализация фотографирования в приложении НКП  на ПТ  
- Камера приложения - для ПТ  должна  управлять системной камерой напрямую, используя системные API 
(например, navigator.b2g.cameras для KaiOS. Приложение самостоятельно отображает видоискатель, делает снимок и 
обрабатывает полученное изображение, не передавая управление сторонним приложениям.
- Отображение видоискателя: 
- Именно приложение, а не какая-то внешняя программа, показывает на экране то, что видит камера. 
Это называется «видоискатель» (viewfinder). Приложение отображает его в своем интерфейсе.
- Съёмка под контролем приложения: Когда пользователь нажимает кнопку «Сделать снимок» в интерфейсе вашего модуля, кадр 
захватывается исключительно кодом приложения. Оно использует для этого встроенные методы (например, getSnapshot()) 
и получает снимок в виде данных, которые может тут же обработать и после закрытия приложения – удалить   
###  📋 Что это значит для проекта
- Таким образом, пользователь предоставляет доступ к камере один раз (при установке или первом запуске модуля ПТ), а дальше
 уже не управляет съёмкой. Модуль сам показывает, что видит камера, сам делает снимок и сам его обрабатывает — всё 
 строго по алгоритму.
- Это гарантирует, что процесс верификации не будет нарушен вмешательством других приложений или случайными 
действиями пользователя, что полностью соответствует модели доверия и изоляции. Всё происходит внутри  приложения, от 
начала до конца.

## 2.4. Хранение ключей и данных
- Система использует строгую иерархию хранения ключей и данных. Каждый тип данных хранится на том устройстве, где он
 максимально защищён, с соблюдением принципа Air Gap (изоляция критических данных от интернета).

- 1. Данные на смартфоне (приложение НКП)
- Псевдонимы, пинкоды подписей, ИНН, паспортные данные:
    • Формат хранения: хеши + соль.
    • Преобразование: необратимое (восстановление исходных данных невозможно).
    • Назначение: идентификация пользователя без раскрытия личности.
## TOTP-ключ (секретный ключ математических часов):
    • Формат хранения: зашифровано.
    • Место хранения: защищённое хранилище на  (Keystore на Android / Keychain на iOS).
    • Важно: ключ хранится на смартфоне только до момента активации ПК-Хранителя. После активации ПК ключ 
    удаляется со смартфона.

- 2. Данные на ПТ (проверочный телефон)
- Мастер-ключ (МК) и TOTP-ключ:
    • Формат хранения: зашифровано (алгоритм AES).
    • Место хранения: энергонезависимая память модуля математических часов.
    • Особенности:
        ◦ ПТ не имеет доступа к интернету.
        ◦ Ключи хранятся в изолированной среде (TEE/StrongBox).
        ◦ Это единственное постоянное место хранения TOTP-ключа до активации ПК-Хранителя.

- 3. Данные на ПК-Хранителе
TOTP-ключ (после переноса с ПТ):
    • Формат хранения: зашифровано.
    • Место хранения: защищённое хранилище модуля математических часов ПК.
    • Особенности:
        ◦ Ключ переносится с ПТ на ПК вручную (через ввод с клавиатуры или через QR-код).
        ◦ После переноса ключ становится постоянным на ПК.

- 4. Данные на флешке (внешний носитель)
- TOTP-ключ (для переноса):
    • Формат хранения: бинарный файл (например, secret.bin).
    • Шифрование: зашифрован.
    • Назначение: временный перенос ключа с ПТ на ПК (или со смартфона на ПК в нулевом состоянии).
    • Важно:
        ◦ Файл существует только во время процедуры переноса.
        ◦ После успешной активации ПК-Хранителя файл на флешке можно удалить.

- 5. Данные в P2P-сети
- Голоса, оценки, проекты, жалобы:
    • Формат хранения: зашифрованы.
    • Ключи шифрования: на основе Мастер-ключа (МК) и пинкода подписи.
    • Особенности:
        ◦ ПК-Хранители не имеют доступа к данным в открытом виде.
        ◦ Расшифровка возможна только на устройстве пользователя (смартфон) при наличии МК и пинкода.

- 6. Данные на бумаге (у пользователя)
- Мастер-ключ (пользовательский формат):
    • Формат хранения: физическая запись (рукой на бумаге).
    • Формат записи: XXXX_XXXX_Слово1_Слово2 (8 цифр + 2 слова).
    • Назначение: последний рубеж восстановления аккаунта.
    • Важно:
        ◦ Мастер-ключ не хранится в цифровом виде на смартфоне.
        ◦ Единственный экземпляр МК в цифровом виде — на ПТ.

- Итог: … Точное место хранения TOTP-ключа — модуль часов на каждом устройстве.
Это изолированный компонент, который генерирует коды и передаёт ключи только на устройства пользователя. 
## Место хранения TOTP-ключа
- Главное правило: TOTP-ключ никогда не хранится в открытом виде или в памяти смартфона. 
- Его постоянное хранение разрешено только в двух местах:
    1. На ПТ (проверочный телефон): В энергонезависимой памяти модуля математических часов 
    (аппаратно-защищённое хранилище TEE). Здесь ключ хранится постоянно с момента регистрации.
    2. На ПК-Хранителе: В защищённом хранилище модуля математических часов ПК. Сюда ключ переносится с ПТ при 
    активации и хранится постоянно.
Временное хранение (до 10 минут): На смартфоне ключ может находиться только временно (в оперативной памяти) 
во время генерации QR-кода или передачи в P2P-сеть. После завершения процедуры ключ немедленно удаляется.
-  Запрещено: Хранить TOTP-ключ в постоянной памяти смартфона, в облачных сервисах, на флешках  кроме временного файла secret.bin, в логах или в открытом виде.
###  2.5  Принципы передачи и исполнения команд
- 2.5.1 Принцип передачи команд
    • Полное приложение на смартфоне не отправляет команды напрямую на ПТ.
    • Вместо этого смартфон показывает код команды (цифру или QR-код).
    • Пользователь вручную вводит этот код на клавиатуре ПТ.
    • ПТ не имеет связи со смартфоном и не знает, была ли нажата кнопка на смартфоне. Он реагирует только на введённый код.
    • Это гарантирует, что даже при компрометации смартфона ПТ остаётся изолированным.

- Обратная связь: После выполнения команды Модуль ПТ отображает результат на своём экране 
(например, показывает мастер-ключ или сообщение об успешном удалении). Данные не передаются обратно на смартфон; 
результат видит только пользователь на экране ПТ.
Это гарантирует, что критически важные данные никогда не покидают изолированную среду ПТ.

## 2.6. Финальная формула НКП.
- НКП = TEE + Шарды на ПК + P2P/MESH + Открытый код с GitHub
- TEE — защита от шпиона с отвёрткой. Ключи не украсть.
- Шарды на ПК — защита от тормозов. 50 млн голосуют за минуту.
- P2P/MESH — защита от "рубильника". Выключить 1 сервер ≠ выключить страну.
- GitHub — защита от "закладок". Любой может проверить код.
- Блокчейна нет. Центрального банка нет. Тормозов нет.

### Пояснения к Шагу 1: Активация и передача ключа математических часов на ПТ
- Встроенный модуль: Приложение НКП содержит встроенный программный криптомодуль для генерации TOTP-кодов (математических часов) с заранее заданными параметрами:
- Длина кода: 8 цифр.
- Шаг смены кода: 60 секунд.
-  Алгоритм: SHA-1 (стандарт RFC 6238).
- Активация и генерация ключа: При запуске процесса регистрации встроенный модуль активируется и генерирует уникальный секретный ключ, который в зашифрованном виде привязывается к номеру проверочного телефона (ПТ), введённому пользователем на предыдущем шаге.
- Формирование QR-кода: Приложение на основе этого сгенерированного ключа формирует QR-код. QR-код содержит секретный ключ и все необходимые настройки (длина кода, шаг).
- Передача на ПТ: Пользователь сканирует QR-код камерой проверочного телефона (ПТ). Модуль часов на ПТ принимает ключ и настройки и теперь имеет точно такие же параметры (8 цифр, позиция # Разделителя: после 4-й цифры, шаг: 60 секунд, например: ####_####).
###  Синхронизация устройств: 
- Всё, часы на ПТ активированы. Ключ на ПТ хранится в энергонезависимой памяти микроконтроллера. Оба устройства: и ПТ, и приложение на смартфоне теперь должны   иметь  одинаковый ключ + одинаковые настройки + одинаковое время. Они должны выдавать идентичные коды в формате ####_####. Дата активации фиксируется (например, 04.07.2026).

### Шаг 2.  Проверка синхронизации часов  
### Проверка  дуальной пары: ПТ – смартфон 
-  После установки математических часов на ПТ, система запрашивает код  с математических часов. Пользователь вводит в приложение на основном телефоне первый 8-значный код, взятый с математических часов (проверка, что часы на проверочном телефоне настроены правильно).  Итог: ПТ- смартфон  – пинкод 1 – запись – сверка с кодом в приложении … установка математических часов проверена. 
- Формат записи пинкода и на ПТ и в приложении одинаков. Это обязательно. 
    • Система ждёт смены кода (60 секунд) и запрашивает второй 8-значный код (новый)
    • Пользователь вводит в приложение на основном телефоне второй  8-значный код.
    • ПТ- телефон 1- пинкод 2 – запись – сверка …  проверено  
- Второй введённый код становится постоянным пинкодом пользователя — его электронной подписью для всех голосований, оценок, жалоб и предложений. Пример кода подписи: 4513_6539
###  Единый TOTP-ключ для всех устройств пользователя
    • При первичной регистрации система генерирует один TOTP-ключ.
    • Этот ключ сохраняется:
        ◦ На ПТ (проверочном телефоне).
        ◦ На флешке (для переноса на ПК-Хранитель).
        ◦ В P2P-сети (зашифрованно, для восстановления и переноса на другие устройства).
- Итак: у нас будет : один ПТ с единым модулем математических часов, один смартфон, одно приложение и один аккаунт, одни часы, один пинкод подписи, один мастер ключ,  один человек- один голос. 
###  Шаг 3. Ввод псевдонима 
- Продолжение процедуры регистрации:
- Далее: 
    • пользователь вводит свой Псевдоним.  (обязательно).
    • Формат псевдонима состоит из трёх частей: Буква латиницы_вымышленное имя_три последние цифры кода с математических часов: Буква_Имя_Цифры. Между частями псевдонима ставится # Разделитель – знак подчёркивания.
… Буква: заглавная латиница 
... Имя: на любом языке, для Кыргызстана: кыргызский, русский, английский. Для других – свой язык на выбор. 
… Три первые цифры кода для псевдонима из 8-ми  значного кода, который вводится из математических часов.   
  ... Пример для Кыргызстана: E_Gvozdika_453

    • Паспорт не используется

### Шаг 4.   Узор, пинкод узора и чернильный отпечаток пальца

... Пользователь берёт два листа тетрадной бумаги. На одном  чертит две решётки как на экране блокировки телефона – 3х3- три лини по горизонтали и три по вертикали: … одна решётка сверху, другая снизу. Расстояние от левого и верхнего краёв бумаги и между решётками 2см = 4 клетки. Длина всех сторон решёток  5( см.) = 10  (клеток ). …  Это черновик _ Лист 1 
    • Узор  …. Внизу на  нижней решётке рисует узор. Линии не пересекаются. Первый угол слева это единица, … справа по середине линии решётки – двойка, правый угол это тройка. Потом снизу от единицы – четвёрка и т.д. И т.д. Узор может начинаться с любой точки.
    • Пин код …. Внизу от нижней решётки  через 2 клетки записывает четыре цифры из тех,  которые находятся на линии узора.  Размер цифр должен поместиться в квадратик из 4-х клеток(1х1см), … в каждой такой клетке своя цифра. Эти четыре цифры будут пинкодом узора.  Например: 4297 
    • Чернильные отпечатки ….  На верхней решётке, размечает кружками точки, на которых будет ставить чернильные отпечатки большого  пальца на узлы решётки, соответствующие цифрам ПИН-кода узора.  Будет четыре отпечатка на узлах, например: 4297 
    • Потом на втором листе – чистовике_ Лист 2, не рисуя решётки пользователь сразу рисует чёрными чернилами: 1. Узор на нижней решётке; 2. Записывает пинкод узора внизу под этой решёткой; 3. Используя штемпельную подушку, ставит на верхней решётке чернильные  отпечатки большого пальца одной из рук на узлы решётки. Узор, пин код узора и  отпечатки должны располагаться точно в тех же местах что и в черновике. 
####  Видеоподсказки и требования к ним 
...  Встроенные видеоинструкции должны иметь интуитивно понятные элементы управления, адаптированные для пользователей с разным уровнем подготовки:
    • Кнопка «Воспроизвести / Пауза» — пользователь может остановить видео в любой момент, чтобы внимательно рассмотреть этап и повторить его на бумаге.
    • Кнопка «Назад» (переход на предыдущий шаг) — позволяет вернуться к началу текущего шага или на один шаг назад в последовательности инструкций. Это особенно полезно, если пользователь пропустил важный момент или хочет пересмотреть этап с самого начала.
    • Индикатор прогресса (ползунок) — помогает визуально оценить, сколько времени осталось до конца ролика, и быстро перемещаться внутри видео при необходимости.
    • Назначение: Эти элементы управления делают обучение интерактивным, доступным и комфортным. Пользователь не должен чувствовать спешки или давления. Он может смотреть видео столько раз, сколько нужно, возвращаться к сложным этапам и копировать действия в своём темпе. Видеоподсказки позволяют избежать ошибок и отправить в систему точные данные, для того, чтобы мастер ключ был верным.
### Фотофиксация:
    • Пользователь фотографирует Чистовик (Лист 2) через внутреннюю камеру приложения и сохраняет во временной папке приложения. …..  Временная папка приложения (tmp на Android/iOS) — это изолированное пространство, принадлежащее только вашему приложению, и она не синхронизируется с облаком и не доступна другим приложениям.
    • Система автоматически распознаёт фото и уведомляет: фото принято или не принято. Если не принято, следует заново проверить записи узоры, размеры цифр, шрифт и заново сфотографировать. Только после принятия фото бумажного чистовика система  начинает собирать все данные регистрации для генерации Мастер ключа.

...  Причины отказа при проверке бумажного шаблона
... Система автоматически проверяет качество фото бумажного шаблона. В случае отказа пользователь получает конкретное сообщение с указанием причины.

... 1. Качество фото
... Система проверяет чёткость, освещение и угол съёмки. При обнаружении проблем пользователь получает одно из сообщений:
    • «Снимок размыт»
    • «Недостаточное освещение»
    • «Неровный угол съёмки»
... Действие пользователя: переснять фото с учётом замечаний.

... 2. Цифры (Пинкод узора)
... Система проверяет наличие и правильность написания четырёх цифр пинкода узора. Возможные сообщения:
    • «Цифры написаны не по стандарту»
    • «Цифры сливаются»
    • «Нет четырёх цифр»
... Действие пользователя: проверить правильность написания цифр, их размер и чёткость, переписать при необходимости и переснять фото.

... 3. Узор
... Система проверяет соответствие узора заданным координатам и толщину линий. Возможные сообщения:
    • «Линии узора слишком тонкие»
    • «Узор не соответствует координатам»
...  Действие пользователя: перерисовать узор более чётко, убедиться, что линии проходят через правильные точки решётки, и переснять фото.

... 4. Отпечатки пальцев
... Система проверяет наличие, расположение и качество чернильных отпечатков. Возможные сообщения:
    • «Отпечатки не на своих узлах»
    • «Отпечатки слабые»
    • «Отпечатки смазаны»
... Действие пользователя: проверить, что отпечатки поставлены на правильных узлах решётки, использовать достаточное количество чернил на штемпельной подушке, чётко прижать палец, и переснять фото.

... 5. Расположение элементов
... Система проверяет, что все элементы (узор, пинкод, отпечатки) расположены в правильных местах на листе. Возможные сообщения:
    • «Не совпадает расположение элементов»
    • «Отсутствует один из элементов»
... Действие пользователя: убедиться, что на листе присутствуют все три элемента (узор, пинкод, отпечатки) и они расположены в соответствии с инструкцией (решётки, расстояния от краёв). При необходимости переделать чистовик и переснять фото.

... Общее правило
... После получения любого сообщения об ошибке пользователь:
    1. Исправляет указанную причину.
    2. Заново фотографирует чистовик (Лист 2).
    3. Повторяет отправку фото в систему.
... Цикл повторяется до тех пор, пока система не примет фото. Только после успешного принятия фото система переходит к генерации Мастер-ключа.
...  Действие пользователя:  Пользователь исправляет указанную ошибку (перерисовывает узор, переписывает цифры, ставит отпечатки заново) и повторяет фото.
    • Если система выдаёт уведомление: фото принято,  только после этого начинается генерация мастер ключа

###  Шаг 5.  Генерация Мастер-ключа 
    • Ядро системы собирает все исходные данные (не хешированные):
        ◦ Узор (графический).
        ◦ Пинкод узора (4 цифры).
        ◦ Геометрию отпечатков.
        ◦ Номера телефонов (основного и проверочного).
        ◦ Псевдоним.
        ◦ Пинкод подписи (8 цифр).
        ◦ Дату регистрации.
    • Система однократно хеширует все эти данные в единую неразрывную строку.
    • На основе этого хеша система генерирует пользовательский формат Мастер-ключа: XXXX XXXX СЛОВО1 СЛОВО2.
    • Мастер-ключ не отображается на экране основного телефона.
### Требования к моменту генерации:  Генерация происходит на устройстве пользователя (основной телефон) без отправки каких-либо данных в сеть.
### Критерий приемки:
    • При попытке извлечь Мастер-ключ из файловой системы устройства (включая рутированное устройство) должна быть невозможность прочитать его в открытом виде.

### Шаг 6. Передача МК на ПТ:
    • Система создаёт QR-код, содержащий Мастер-ключ в пользовательском формате.
    • На экране основного телефона появляется уведомление:
... «Мастер-ключ создан. Отсканируйте QR-код камерой проверочного телефона (ПТ) для сохранения».
    • Пользователь сканирует QR-код камерой ПТ.
    • ПТ сохраняет Мастер-ключ в пользовательском формате  в аппаратно-защищённом хранилище (TEE/StrongBox).
###  Затирание следов:
    • После успешного сканирования QR-кода основной телефон(смартфон) затирает (перезаписывает нулями) все следы Мастер-ключа в оперативной памяти и временных файлах.
    • На основном телефоне не остаётся ни Мастер-ключа, ни QR-кода.
###  Запись МК на бумагу (с ПТ):
    • Для переписки МК на бумагу пользователь:
    • Смотрит  на основном телефоне: «Профиль → Безопасность → Показать Мастер-ключ».( код  04 Показать МК, смотрите пункт 2.5.2. )
    • Пользователь открывает на ПТ  приложение и нажимает на кнопку 04 –точно такой же код  как и на смартфоне. 
    • Модуль ПТ отображает Мастер-ключ на своём экране.
    • Пользователь переписывает Мастер-ключ с ПТ на отдельный бумажный лист.
    • После завершения пользователь закрывает экран на ПТ.
### Требования к формату отображения для пользователя:
   ...  1. Критически важно различать две вещи:
        ◦ Внутренний (настоящий) Мастер-ключ: Длинная криптостойкая строка, которая хранится в системном хранилище.
        ◦ Отображаемый (пользовательский) Мастер-ключ:                        
        ◦  комбинация цифр и слов:  XXXX_ XXXX_ Слово1_ Слово2, которая генерируется из внутреннего ключа для отображения пользователю на экране.
... 1. Для удобства ручной записи на бумажный носитель Мастер-ключ должен отображаться пользователю в следующем формате:
        1. 8 цифр, сгруппированных по 4 через знак подчёркивания                      (например: 1463_5196).
        2. Два слова на русском или кыргызском языке (в зависимости от языка интерфейса), # Разделенных знаком подчёркивания  (например: Солнце_Ветер).
... Слова должны выбираться из заранее подготовленного словаря объемом не менее 4096 уникальных слов (12-битная энтропия на каждое слово), что соответствует общепринятым стандартам мнемонических фраз (BIP-39).
...   Формат отображения является производным от внутреннего криптографического ключа и не снижает его энтропию (внутренний ключ остается длиной 128+ бит).
...   Общий вид Мастер ключа, пример: 1463_5196_Солнце_Ветер
### Шаг 7. Автоматический  контроль и кнопка отправить
## Финальная кнопка «ОТПРАВИТЬ» строго заблокирована. Система зажигает интерактивные галочки [ ✓ ] принятия по каждому пункту чек-листа:
... 1. Номера телефонов, которые он указал,  (основной и один проверочный), Псевдоним,  ПИН-код подписи,  фото листа с чернильным отпечатком большого пальца правой или левой руки,  с узором и  пинкодом узора, текущая дата, сгенерированный системой Единый Мастер-ключ.
...  2. Контрольное дублирование:  После генерации  Мастер-ключа  и передачи его на ПТ его открытая копия в оперативной памяти приложения должна быть затерта (перезаписана нулями).
... 3. После этого система выставляет галочку.
    • Если все сверки пройдены — регистрация завершается.
## Завершение регистрации
... 1. Активация кнопки «Пуск»: Как только все галочки (номера телефонов, псевдоним и другие  загорелись зеленым, на экране активируется кнопка «ОТПРАВИТЬ».
... 2. Реальная отправка: Пользователь ставит подпись и  нажимает на кнопку «ОТПРАВИТЬ», и сформированный пакет всех данных единым монолитным узлом уходит в P2P-сеть.
## Тотальное уничтожение следов
... В ту же микросекунду память телефона полностью зачищается. Приложение выдает финальное уведомление:
«Регистрация завершена успешно! Ваши оригинальные фото бумажных записей  безвозвратно удалены из оперативной и постоянной памяти устройства. Псевдоним привязан к ПИН-коду подписи и вашей дуальной паре телефонных номеров. Единственный экземпляр Мастер-ключа сохранен на вашем проверочном телефоне. Перепишите его на бумагу
## **Значение мастер ключа **
-  Пинкод на бумажке — это страховка на случай, если вы забудете свой ежедневный пароль. Мастер-ключ на бумажке — это страховка на случай, если кто-то попытается украсть вашу личность.
- Убирая Мастер-ключ, вы лишаете систему возможности отличить вас от хакера, который просто купил базу телефонных номеров. - Убирая Мастер-ключ, вы оставляете единственный рубеж обороны (Пинкод), который можно перехватить или подсмотреть. С Мастер-ключом у вас появляется «бункер», в который не могут проникнуть даже при наличии Пинкода и паспорта. …. Система скажет  хакеру: «номера телефонов, пинкод, паспорт и псевдоним совпадают, но для смены статуса введи Мастер-ключ, который был создан в день регистрации.  Хакер не знает Мастер-ключ, и система его отсекает.
    • При утере пользователем Мастер-ключа, его восстановление возможно с помощью фото отпечатков пальца, узора и пинкода узора.  Пользовательский формат при этом не меняется. 
    • При утере всех данных пользователь может перерегистрироваться заново с помощью каких либо регистрационных данных. При этом предыдущий  аккаунт анулируется.

## Активация ПК-Хранителя (передача ключа через P2P-сеть)
Поскольку ПК-Хранитель важен именно вначале зарождения сети НКП, то пункт об активации ПК-хранителя расположен именно  здесь, в # Разделе анонимной регистрации. Если отложить активацию ПК-Хранителя «на потом», сеть не будет работать, потому что некому хранить данные. Пользователь сам решает, устанавливать ему приложение на ПК или нет. Если да, то: 
Этап 1. Идентификация пользователя на ПК
    1. Пользователь устанавливает на ПК приложение «НКП-Хранитель» (версия без модуля голосований).
    2. При первом запуске пользователь вводит на клавиатуре ПК следующие данные (те же, что и при первичной регистрации):
        ◦ Псевдоним (например, E_Gvozdika_453).
        ◦ Номер основного смартфона.
        ◦ Номер проверочного телефона (ПТ).
        ◦ Мастер-ключ (МК) в пользовательском формате (например, 1463_5196_Солнце_Ветер).
    3. ПК сохраняет эти данные в зашифрованном виде и привязывает их к себе. Теперь ПК «знает», какому пользователю он принадлежит.
    4. Проверка: ПК сверяет введённый МК с хешем, который есть в P2P-сети (если сеть доступна). Если данные не совпадают — активация блокируется с сообщением: «Введённые данные не соответствуют зарегистрированному пользователю».

Этап 2. Передача TOTP-ключа с ПТ на ПК (офлайн, Air Gap)
    5. Пользователь открывает на ПТ модуль математических часов и нажимает кнопку «Показать TOTP-ключ».
    6. ПТ отображает TOTP-ключ в пользовательском формате (например, 56_143-5196-Космос).
    7. Пользователь вручную вводит этот ключ на ПК в приложении «НКП-Хранитель», используя скрытую клавиатуру (защита от кейлоггеров).
    8. ПК сохраняет TOTP-ключ в зашифрованном виде в модуле математических часов, привязывая его к данным пользователя (псевдоним, телефоны, МК), введённым на Этапе 1.
    9. Проверка: ПК запрашивает текущий код с ПТ. Пользователь вводит код с ПТ. Если код совпадает — TOTP-ключ на ПК активирован.

Этап 3. Привязка ПК к P2P-сети (онлайн)
    10. На ПК пользователь нажимает кнопку «Активировать ПК-Хранитель в сети».
    11. ПК генерирует уникальный номер сессии (случайная строка, например, a7f3k9m2) и формирует QR-код, содержащий:
        ◦ Номер сессии.
        ◦ Данные пользователя (псевдоним, номера телефонов, хеш МК).
        ◦ TOTP-ключ (тот же, что пользователь ввёл вручную на шаге 7).
    12. Пользователь сканирует QR-код камерой смартфона через приложение НКП.
    13. Приложение на смартфоне считывает из QR-кода данные пользователя, номер сессии и TOTP-ключ. Оно сравнивает полученные данные пользователя с теми, что сохранены на смартфоне при регистрации:
        ◦ Если данные совпадают → смартфон подтверждает, что это именно тот пользователь.
        ◦ Если данные не совпадают → передача блокируется.
    14. После успешной проверки смартфон передаёт в P2P-сеть (libp2p) пакет данных:
    • Данные пользователя
        ◦ Номер сессии.
        ◦ TOTP-ключ.
    15. ПК находит в P2P-сети свой номер сессии  и сравнивает:
        ◦ TOTP-ключ из сети с тем, что пользователь ввёл вручную (шаг 7).
        ◦ Данные пользователя (псевдоним, телефоны) с теми, что были введены на Этапе 1.
        ◦ Если всё совпадает → ПК подтверждает, что это именно его сессия.
        ◦ Если не совпадает → активация блокируется, сессия аннулируется.
    16. Для финальной проверки ПК ещё раз запрашивает текущий код с ПТ. Пользователь вводит код.
    17. Если код совпадает → активация завершена. ПК-Хранитель становится полноценным узлом P2P-сети.
    18. Номер сессии и TOTP-ключ удаляются из P2P-сети. В сети остаётся только хеш ключа для будущих проверок.

Примечание к активации ПК-Хранителя
    • Если в регионе нет других активных ПК-Хранителей, P2P-сеть может быть недоступна для синхронизации.
    • В этом случае система:
        ◦ Отображает сообщение: «В вашем регионе пока нет других Хранителей. Синхронизация возможна после появления как минимум одного активного узла. Пожалуйста, подождите или пригласите других пользователей».
        ◦ Сохраняет данные локально и ожидает появления сети.
## Регламент работы ПК-Хранителей
1. Статус Хранителя.
Каждый пользователь добровольно может зарегистрировать свой личный ПК для выполнения функций сервера в своём сегменте-шарде. Этот ПК называется Хранителем.
Хранитель — это не банковский сервер 24/7. Это волонтерский ПК. Он имеет право выключаться тогда, когда удобно его владельцу.
2. Минимальное количество Хранителей (Для Кыргызстана).
Приложение не переходит в рабочий режим, пока в сети не зарегистрировано минимум 7 активных Хранителей. Если нет нужного минимума, система держит режим "только чтение" (голосование блокируется).
3. Хранителей должны быть распределены в семи областях Кыргызстана. Один регион не должен содержать более 50% всех Хранителей.
4. Формат позывного и география.
При регистрации Хранителя фиксируется только его принадлежность к одному из городов (регионов). Точные GPS-координаты, MAC-адреса и IP-адреса не сохраняются в открытом виде.
    • Формат позывного: [Регион]_[Тип]_[Порядковый номер]
    • Пример: BISHKEK_K_001, TALAS_K_007 (где К — Кеерег / Хранитель).
    • Каждый Хранитель обслуживает пользователей, выбравших при голосовании его регион. Если Хранителей в регионе нет, пользователь подключается к ближайшему по ping (< 100 мс).
    5.  Штатный режим работы (Дневная сессия).
    • Включение: 09:00 утра по местному времени региона.
    • Отключение: 20:00 вечера по местному времени региона.
    • В 20:00 Хранитель прекращает прием новых транзакций (голосов). Все накопленные данные фиксируются на диске в виде локального снепшота.
    • Владелец ПК вправе выключить компьютер немедленно после 20:00 или через час (по своему усмотрению). Система НЕ ожидает завершения репликации с другими регионами.
6. Синхронизация и восстановление (Дельта-синхронизация).
    • Если выключение произошло до завершения репликации, на диске сохраняется флаг sync_pending = true.
    • При включении ПК (в 09:00 или позже) Хранитель проверяет флаг, запрашивает у 2–3 соседей голоса за период отсутствия и применяет данные.
    • Время досинхронизации не должно превышать 15 минут. Если данные не получены, Хранитель запускается с пометкой sync_warning.
7. Режим планового отсутствия (Vacation Mode).
Владелец ПК имеет право приостановить участие в сети по уважительным причинам (болезнь, отпуск, командировка). Он фиксирует остановку ПК- Хранителя в бланке: Form № 0.7 – Бланк временного отключения ПК-хранителя
    • Для активации необходимо в интерфейсе указать дату начала и возврата.
    • Система запускает миграцию данных на резервные Хранители (не более 15 минут).
    • После миграции ПК выключается. Статус Хранителя сохраняется. При возврате данные восстанавливаются от соседей.
 
8. Режим экстренного отключения и динамической ротации Хранителей (Без предупреждения). 
1. Штатный режим (с 1 по 24 число месяца):
   - Порог фиксации сбоя: 12 часов.
   - Порог перераспределения данных и исключения: 24 часа.
2. Мобилизационный режим «Голосование» (с 25 по 31 число месяца):
   - Порог фиксации сбоя и PUSH-оповещения: 1 час неактивности.
   - Порог экстренного перераспределения нагрузки (ребалансировка шардов): 6 часов неактивности.
   - Задача: Обеспечить бесперебойную регистрацию бланков даже при одновременном отключении до 30% Хранителей.
9. Автоматическое восстановление:
   - При включении ПК- Хранителя система без человеческого фактора сверяет хэш-суммы, скачивает недостающие бланки и возвращает Хранителя в активный список.
3. Условия автоматического возвращения Хранителя в сеть: - Статус восстановления: При включении ПК после сбоя узел переходит в режим «Синхронизация». В этом режиме узел не участвует в первичной обработке новых бланков, пока не восстановит историю. - Автоматическая сверка (Быстрая синхронизация): Программа сверяет хэш-дерево (Merkle Tree) своего архива с соседними 6 Хранителями, докачивает недостающие шарды за период отсутствия и подтверждает целостность базы. - Полноценный возврат: Как только хэш-суммы совпали на 100%, статус узла автоматически меняется на «Активный Хранитель», и ПК снова полноценно обслуживает сеть. - Исключение человеческого фактора: Возврат в сеть происходит абсолютно автоматически на основе криптографических проверок, без необходимости предоставления справок, объяснительных или ручного одобрения администраторами

 ## Система защиты: что от чего защищает

Каждый элемент системы защищает свой фронт. Нет одного «супер-ключа», который бы всё решал. Есть система, где каждый слой защищает от своей угрозы.
    • Псевдоним + пинкод + ПТ → защищают вход.
    • МК + хеши → защищают данные от хаккеров
    • ПТ + Device ID+ бумажные записи → защищают от фейков.
    • P2P + хеши+ ПК- Хранители(автономные сервера) → защищают от удаления, просмотра и подделки истории.
Социальный барьер для фейков
Чтобы переломить результаты голосований, надо на каждые 1 млн. пользователей создать или подкупить 500 тыс человек, а в открытых аккаунтах они никогда не пройдут в круг доверенных лиц, т.к. там нужно завоевать доверие в живом формате, в работе с людьми.
Это математическая и социальная защита одновременно:
    • Математическая: 500 тысяч фейков на 1 млн реальных пользователей — это стоимость, логистика, риск.
    • Социальная: Доверие не покупается и не создаётся массово. Его можно только заслужить годами.
Фейки не могут быть созданы массово- сотнями тысяч и миллионами,  быстро и скрытно. Это потребует многих лет подрывной или подпольной деятельности правительства и  неизбежно будет раскрыто. А за этим последуют обнуление рейтинга высокопоставленных лиц и отставки.

# Раздел 4 Открытая регистрация
4.1  Открытый (верифицированный) режим (добровольно)
Переход пользователя из анонимного статуса в открытый осуществляется строго на добровольной основе (для участия в Курултае, выдвижения проектов или работы в органах управления). Этот процесс защищен сквозной криптографической проверкой подлинности, исключающей фейковые аккаунты или хакерский перехват личности.
Процедура регистрации аналогична анонимной: 
Бланк для открытой регистрации Form-0.1 
… После завершения анонимной регистрации активирована кнопка: Открытый режим. ( смотрите # Раздел о бланках)
    • Подача заявления и раскрытие данных: Пользователь приступает к заполнению бланка: предоставляет полный пакет документов: Фамилия, имя, отчество, фото оригинал паспорта (ID-карты) с обеих сторон, ИНН, email, рабочие номера телефонов, те же, что и при анонимной регистрации (основные с установленным приложением и один проверочный) и фактический адрес проживания.
    • Новый пинкод подписи вводится с ПТ, который математически не связан с прежним анонимным ПИН-кодом подписи. Заново устанавливать математические часы не нужно. Все прежние телефоны уже привязаны к анонимному аккаунту и связываются с открытым. 
    • Псевдоним, созданный при анонимной регистрации сохраняется, но в открытом профиле отображается ФИО. Псевдоним не удаляется, а просто перестаёт быть публичным идентификатором. Вместо псевдонима, в открытых голосованиях,  - ФИО. 
    • Пользователь внутренней камерой приложения фотографирует паспорт с двух сторон.
    • Пользователь вручную вводит свои паспортные данные (серия, номер, ФИО и другие) для сверки с MRZ (автоматическая проверка) и для хеширования.
Система сравнивает введённые данные с извлечёнными из MRZ. Если совпадают — паспорт подлинный (не подделка)
    • После сверки все фото и введённые данные удаляются	В системе остаются только хеши (для проверки в будущем).
    • Узор, пинкод узора и чернильный отпечаток пальца: …  пользователь фотографирует эти бумажные записи внутренней камерой приложения также  как и фото паспорта для проверки личности. Система сохраняет фото во внутренней папке  проверяет и после этого удаляет фото, не сохраняя его. Система не хранит фото, она хранит хеш. При повторной проверке она создаёт новый хеш из нового фото и сравнивает его со старым хешем. Это и есть математическая защита.
    • Фото паспорта не хешируется: Хеш фото не имеет смысла для проверки подлинности — его нельзя сравнить с другим фото. Фото нужно только для извлечения приложением  MRZ и для сравнения с  введёнными данными,  после чего оно уничтожается.
    • ФИО — единственное поле, которое остаётся в открытом виде (если пользователь выбрал открытое голосование). Все остальные данные — только в виде хешей.
    • Критический рубеж безопасности (Предъявление Мастер-ключа): Для запуска процесса верификации система в обязательном порядке запрашивает Единый Мастер-ключ, сохраненный пользователем на его бумажном носителе при первичной регистрации.
    • Без ввода вручную корректного Мастер-ключа любая попытка верификации автоматически блокируется системой и расценивается как хакерская атака или попытка создания фейкового профиля.
    • Статус и профиль: После успешной проверки  Мастер-ключа и документов сеть производит его обновление.  Участник получает официальный статус «Верифицированный участник». 
    • Завершение регистрации:  пользователь нажимает кнопку  Отправить.
    • С этого момента его реальные ФИО будут публиковаться  в профиле платформы, в результатах голосований, решений, сообщений,  а рабочий Псевдоним для открытых действий больше не используется. 
    • Мастер ключ  в пользовательском формате остаётся таким же как и при анонимной регистрации, добавляются  лиш хеши новых  данных к уже существующим хешам.                                                                                                  
    • Результат: Один мастер-ключ содержит все данные аккаунта (как анонимные, так и открытые). Один человек — один мастер-ключ. При переходе от анонимной регистрации к открытой мастер-ключ дополняется, а не пересоздаётся. Это сохраняет историю аккаунта и упрощает управление.
    • При открытой регистрации пользователь проходит тройную проверку 1. через номера телефонов и псевдонимов; 2. Через мастер ключ, 3. Через бумажную запись узора, пинкода узора и отпечатков пальцев, - созданные ранее в день анонимной регистрации.

Логика для «нулевого» состояния системы: когда никого нет кроме первого пользователя.
Активация первого ПК-Хранителя («нулевой узел»)
Перенос TOTP-ключа на ПК через флешку (бинарный файл)
    1. Приложение на смартфоне генерирует точно такой же ключ TOTP как и для ПТ и экспортирует TOTP-ключ в бинарный файл (например, secret.bin).
    2. Пользователь копирует файл на USB-накопитель (флешку).
    3. ПК отключается от интернета (режим Air Gap).
    4. Флешка подключается к ПК.
    5. Приложение «НКП-Хранитель» на ПК считывает бинарный файл и извлекает ключ.
    6. Ключ сохраняется в зашифрованном виде на ПК в модуле часового механизма. 
    7. Флешка извлекается и может быть удалена (или перезаписана).
Важно: Ключ не отображается на экране ПК (только в зашифрованном хранилище). Пользователь не вводит ключ вручную. Математические часы загружаются на ПТ и ПК одинаково (один и тот же ключ, одинаковые настройки).

- 5.1  Восстановление данных из P2P-сети

        1. Пользователь вводит Мастер-ключ (МК) и пинкод подписи.

Каждый бланк (голосование, сигнал, оценка) получает:

    • Поле для подписи (пинкод пользователя).
    • Дату и время (фиксация момента голосования).
6.2 Сбор голосов и хеширование итогов
    • Все голоса собираются в защищённом контейнере в открытом виде (доступном только системе).
    • Защита контейнера обеспечивается кодировщиками (шифрование, изоляция, контроль доступа).
    • Подсчёт голосов происходит напрямую (математика работает с открытыми данными внутри контейнера).
6.3. Хеширование итогов голосования (для архива)
    1. Публикация результатов: После завершения голосования система подсчитывает голоса и отображает итоги в соответствующем бланке: Form № … /итог Этот бланк виден всем пользователям.
    2. Фиксация хеша: После отображения результатов система вычисляет хеш (цифровой отпечаток) заполненного бланка итогов. Хеш включает в себя все данные, отображённые в бланке.
    3. Архивация: Вычисленный хеш сохраняется в архиве (наряду с другими хешами).
    4. Проверка подлинности: Если правительство или любой другой пользователь захочет проверить подлинность результатов, он может нажать кнопку «Проверить». Система заново вычислит хеш текущего бланка и сравнит его с сохранённым хешем.
        ◦ Если хеши совпадают → бланк подлинный, данные не изменены.
        ◦ Хеш результатов служит доказательством целостности итогов голосования
        ◦ Если хеши не совпадают → бланк был изменён (подлог).
        ◦ 
    5. Готовность к новым данным: После отправки  хеша в архив, контейнер (память, где шёл подсчёт) очищается и готов к приёму данных следующего голосования.
    6.  Пустые бланки не хешируются.

6.4   Жизненный цикл бланка в личном кабинете гражданина:
    • После успешной отправки заполненного бланка, данный экземпляр бланка в личном кабинете пользователя получает статус "Архив" и перемещается в # Раздел "История".
    • Одновременно на место использованного бланка система автоматически выдаёт новый, чистый экземпляр бланка того же типа.
    • У пользователя всегда должен быть доступен актуальный бланк для каждого типа действия. Ситуация "бланки закончились" недопустима.
    • Исключение: если бланк сезонный/одноразовый, то после использования он уходит в архив без замены. Список таких бланков согласовывается отдельно.
    • Статус использованных бланков: 
    • После использования бланк становится недействительным для нового голосования, но не удаляется. Он сохраняется в архиве как доказательство голосования. 

6.5  Двухэтапная подпись (универсальное правило)
При оформлении любого бланка (голосование, заявка на денежный перевод, жалоба, предложение, проект, обращение) пользователь обязан пройти двухэтапную подпись:
    1. Ввести текущий код с ПТ (одноразовый TOTP-код, действует 60 секунд).
    2. Ввести постоянный пинкод подписи (созданный при регистрации).
Только после успешной проверки обоих факторов бланк считается подписанным и отправляется в систему.

# Раздел 8  Единое правило подсчёта голосов для всех бланков
- На всех бланках голосования по любому вопросу фиксация ответов происходит по единому правилу:
- По каждому пункту голосования гражданин выбирает один из трёх вариантов (например: «Да», «Нет», «Воздержался»).
- Каждый участник в соответствующей ячейке (на пересечении строки и столбца) ставит единицу (1) в том варианте, который он выбирает.
- Единица — это числовой маркер, который участвует в математических операциях.
- Галочка (✓) не используется,  за исключением одного случая при заполнении формы № 1.1: …  Form № 1.1 — Оценка деятельности Главы государства (по системе Лао Цзы)
- При подведении итогов система автоматически суммирует все единицы по каждой строке (пункту голосования) и по каждому варианту («Да», «Нет», «Воздержался» и другим вариантам  положительных или отрицательных ответов).
- Доля каждого варианта вычисляется по формуле:
- Доля варианта = (Количество единиц по варианту / Общее количество единиц по строке) × 100%
- Результат округляется до одного десятичного знака (например, 45.6%).
- Сумма долей по трём вариантам всегда равна 100%.
- Формула универсальна и не зависит от названий вариантов ответа («Да/Нет/Воздержался», «Подтверждаю/Не подтверждаю/Воздержался», «Одобряю/Не одобряю/Воздержался» и т.д.).

#### 9.1 Блокировка сообщений и аккаунтов за экстремистские сообщения

- Экстремистские сообщения (призыв к насилию, расправе, госперевороту) не публикуются. После нажатия на кнопку  Отправить они заносятся в отдельную таблицу блокировок: Form № C_003- категория С
- В таблице  блокировок указываются: псевдоним автора, текст его сообщения, дата и время.
- Если автор исправил сообщение сразу после первого  предупреждения системы, до нажатия на кнопку Отправить, то оно не вносится в бланк блокировок.
- Если автор не исправил сообщение и нажал на Отправить, то сообщение блокируется и  фиксируется как нарушение и заносится в  таблицу блокировок: Form № C_003- категория С
… Три нарушения,  после третьего, - это первая  блокировка на  год.  
- Следующие три нарушения, - после третьего,  - вторая блокировка аккаунта на год.
- Следующие три нарушения, - после третьего, - третья  блокировка аккаунта навсегда. 
- Итак: если будут зафиксированы три блокировки, независимо от времени между ними, то аккаунт остаётся заблокированным навсегда. Счётчик блокировок идёт не за год, а за всё время существования аккаунта.

### 9.2. Процедура восстановления заблокированного аккаунта
    • Заблокированный аккаунт не может быть восстановлен автоматически.
    • Пользователь теряет доступ ко всем функциям системы (голосование, оценки, жалобы, предложения).

    • Снятие блокировки возможно после того как будет сформирован совет доверенных лиц (медиаторов), которые имеют право рассматривать апелляции заблокированных пользователей.
 ** Процедура восстановления:**

- Доверенные лица принимают решение большинством голосов, составляется Акт: Акт на снятие блокировки или Акт в отказе на снятие блокировки.  
            ▪ Снять блокировку (с полным доступом ко всем функциям).
            ▪ Отказать в снятии блокировки. (аккаунт остаётся заблокированным навсегда). ( смотрите форму 004 в категории С )

 # Раздел 9  Защита приложения и данных
### Защита результатов голосований
### 9.1. Порядок проверки учета голоса гражданина
1. Квитанция гражданина.
... После каждого голосования система выдает гражданину в Личный кабинет электронную квитанцию. Квитанция содержит персональный хеш-код голоса. Квитанция сохраняется в разделе "История" в виде QR-кода.
... Персональный хеш-код голоса (Hash) вычисляется как: SHA-256( Псевдоним + Пинкод подписи + Время голосования по времени ПК-Хранителя  + Номер бланка + Выбранный вариант голосования ). Это гарантирует, что хеш уникален для каждого голоса и не может быть переиспользован или подделан.
2. Публичная доска хешей.
... Все хеши голосов, принятые с 09:00 до 20:00, ежедневно публикуются в разделе аналитических таблиц (Form-.../итог) в виде обезличенного списка по регионам. Список публикуется в виде таблицы с колонками: Регион | Хеш-код голоса | Время голосования по времени ПК-Хранителя.    
3. Проверка.
...Гражданин, если пожелает,  вводит номер своего хеш-кода из квитанции в поисковое поле. Система открывает список хешей его региона, где он голосовал и  автоматически прокручивает таблицу к строке с этим хешем, выделяя её (например, подсветкой или рамкой). Гражданин находит в этом списке свой хеш-код. Наличие хеша в списке является доказательством учета голоса.
Такой подход делает систему не просто «честной», а зримо честной. Пользователь не просто получает ответ — он видит доказательство своими глазами.
4. Защита от подлога.
Ежедневно в 20:00 по времени ПК-Хранителя для всего массива хешей региона вычисляется итоговый контрольный код (Merkle-Root). Итоговый контрольный код публикуется в системе. Любое изменение, добавление или удаление хотя бы одного хеша приводит к изменению итогового контрольного кода. Сверка по контрольному коду является математической гарантией целостности данных.

#### 1. Распределённое хранилище (P2P)
- Требование
- Система не должна иметь центрального сервера. Все данные (голоса, оценки, жалобы, предложения, проекты) хранятся в децентрализованной P2P-сети на устройствах участников. Это обеспечивает невозможность блокировки или удаления данных властями.
####   2. Функциональные требования
... Приложение автоматически подключается к P2P-сети при запуске.
...  Новые голоса, жалобы, предложения распространяются по сети в реальном времени (задержка — секунды, а не часы).
...   Должен быть реализован механизм «догоняющей синхронизации» (catch-up sync): если телефон был выключен несколько дней, при включении он должен быстро (за 1–2 минуты) получить все изменения, произошедшие в его отсутствие, и восстановить актуальное состояние.
...  Данные не транслируются «всем подряд». Система запрашивает только то, что нужно пользователю в данный момент (по ID, по поиску, по теме).
-... Старые жалобы и предложения автоматически удаляются из сети по истечении срока (TTL): жалобы — 1 год, предложения — 2 года, возмущения — 6 месяцев. Итоговые результаты голосований хранятся постоянно.
...  Пользователь может отказаться от участия в хранении чужих данных (опция «Только голосовать»), чтобы экономить трафик и память.
... Приложение работает без интернета (голоса сохраняются локально и отправляются при появлении сети).
... После подключения к сети изменения синхронизируются в фоне, без потери данных.
...  Пользователь, включивший телефон после двух дней бездействия, видит актуальные рейтинги и жалобы в течение 1–2 минут.
... Никакой внешний администратор не может удалить или изменить данные в сети.
#### 3. Неизменяемость архива (без блокчейна)
... Ежесуточный хеш всех изменений
...  Раз в сутки система вычисляет хеш-сумму всех новых записей (голоса, оценки, проекты, жалобы).
...  Гарантия целостности обеспечивается публичностью хешей и децентрализованным хранением данных.
...   Публикация хеша
- Вычисленный хеш публикуется в общедоступном месте (например, в файле hashes.log на GitHub, а также рассылается по P2P-сети).
#### 4.  Логирование (неизменяемый журнал событий)
- Система автоматически логирует следующие события:
- Создание, изменение, удаление любого бланка (кто предложил, когда, результат проверки)

- Запуск и остановка системы

####  9.1  Стратегия абсолютной живучести и безопасности (Air Gap & P2P-Survivability)
- Для обеспечения непрерывности управления (Continuity of Power) и защиты от глобальных киберугроз, архитектура НКП (ЭКА – элдик курултай аянтчалары) реализует два взаимосвязанных протокола:
#### 1. Протокол физической изоляции (Air Gap)
- В основе безопасности данных лежит международный стандарт Air Gap («воздушный зазор»).
• Механизм: Критически важные операции (подписание транзакций, генерация математических ключей, валидация голосования) производятся исключительно на втором устройстве, не имеющем физического доступа к сети Интернет.
• Результат: Это делает удаленный взлом, подмену данных или вмешательство ИИ технически невозможным, так как «золотая копия» волеизъявления гражданина хранится в изолированной среде.
#### 2. Децентрализованная дистрибуция (Anti-Block System)
- Система спроектирована как «цифровая гидра», независимая от централизованных корпоративных сервисов (Google Play, App Store и облачных серверов).
• Независимость от магазинов: В случае взлома, саботажа или блокировки приложения в централизованных маркетах, система переходит в режим автономного распространения.
• P2P-передача: Каждое установленное приложение обладает функцией прямой передачи установочного файла (.apk) на другие устройства через Bluetooth, Wi-Fi Direct или Mesh-сети без участия интернета.
• Верификация подлинности: Подлинность любой копии приложения, полученной из альтернативных источников (GitHub, зеркала, передача от соседа), автоматически подтверждается через цифровую подпись автора, которая валидируется офлайн-ключом на втором устройстве пользователя.

# Раздел 12. Критерии приемки Этапа 1
**Программа считается успешно реализованной и готовой к тестированию только при выполнении следующих условий.**

12.1. Регистрация и идентификация
    1. Пользователь может зарегистрироваться анонимно и открыто (добровольно). После анонимной регистрации кнопка «Открытый режим» становится активной.  Граждане, проживающие за рубежом регистрируются вначале открыто.
    2. Регистрация требует второго телефона без интернета (ПТ) с TOTP-генератором (8 цифр, шаг 60 секунд). При регистрации система запрашивает код с ПТ. Без кода регистрация невозможна.
    3. Пинкод подписи (8 цифр) создаётся как второй код с ПТ и хранится в виде хеша + соль. Восстановление пинкода невозможно. Замена пинкода возможна через Form-A-003 «Управление аккаунтом» 
    4. Мастер-ключ (МК) создаётся на основе всех регистрационных данных и передаётся на ПТ. На смартфоне МК не хранится. После передачи МК на ПТ его копия на смартфоне затирается (перезаписывается нулями).
    5. Пользователь может восстановить аккаунт после удаления приложения через МК и пинкод. При восстановлении система запрашивает МК и пинкод и возвращает зашифрованные данные из P2P-сети.
12.2. Бланки и голосования
    6. После регистрации пользователь получает стартовый набор бланков. В личном кабинете отображаются все доступные бланки.
    7. Любой гражданин может предложить проект НХК через Form №2 «Предложения по проектам, инициативы». Форма содержит поля: название, категория, описание, ссылка на аннотацию (не более 3 листов А4), ссылка на полный проект (любой объём на Google Диске).
    8. Голосование по проектам: проект считается принятым, если голосов «ЗА» больше, чем «ПРОТИВ». Кворум не требуется. Система подсчитывает голоса и выводит результат.
    9. Граждане могут оценивать госслужащих через фиксацию фактов с доказательствами через Form № 1.2 «Фиксация нарушений и положительных деяний госслужащих». Форма содержит поля: ФИО госслужащего, должность, описание факта, ссылки на доказательства.
    10. Единая система подсчёта голосов — по каждому пункту голосования гражданин выбирает один из трёх вариантов («Да», «Нет», «Воздержался»). Система автоматически подсчитывает доли в % по формуле: (количество единиц по варианту / общее количество) × 100%.

12.3. Статистика нарушений и цикл контроля
    •     В профиле госслужащего отображаются 3 столбца статистики: количество нарушений, % голосов, количество проголосовавших,. При открытии профиля госслужащего отображаются все 3 столбца.
    •      Частота нарушений за год: 5–9 → уведомление президенту и НКП; 10+ → автоматическое направление материалов в Генпрокуратуру. Система автоматически отслеживает количество нарушений и отправляет уведомления при достижении порогов.
    •     Цикл контроля: если госслужащий не ответил на претензию или не исправил нарушение в течение 30 дней, система инициирует повторное голосование. Цикл повторяется каждые 30 дней до устранения нарушения.

12.4. Безопасность и защита данных
    • Air Gap: Критические операции (подпись, генерация ключей) выполняются только на ПТ (устройство без интернета). ПТ не имеет доступа к интернету. Все критически важные данные передаются через QR-коды или ручной ввод.
    •      P2P-сеть: Все данные (голоса, оценки, проекты) хранятся децентрализованно на ПК-Хранителях. Отсутствует центральный сервер. Данные синхронизируются через libp2p.
    •      TOTP-ключ хранится только на ПТ и ПК-Хранителях. На смартфоне ключ не хранится. При проверке ключ на смартфоне отсутствует. Все операции с ключом выполняются через ПТ и ПК.
    •      Мастер-ключ хранится в пользовательском формате на ПТ и на бумаге. На смартфоне МК отсутствует. При передаче МК на ПТ его копия на смартфоне затирается.
    •      Логирование: Все события (голосования, блокировки, изменения бланков) фиксируются в неизменяемом журнале. Логи невозможно изменить или удалить. Хранятся не менее 5 лет.
    •      Система должна полностью соответствовать # Разделам 8 - 9  – безопасности и открытости кода

12.5. Автоматическая фильтрация и блокировки
    • Уровень 1: Сообщения с призывами к насилию блокируются с предупреждением. При отправке сообщения с угрозами система выдаёт предупреждение и блокирует публикацию.
    •      Уровень 2: После 3-х предупреждений аккаунт блокируется на год. Система фиксирует 3 нарушения и автоматически блокирует аккаунт.
    •     Блокировка аккаунта: 3 блокировки → пожизненная блокировка. Система отслеживает количество блокировок и при достижении 3-х блокирует аккаунт навсегда. Счётчик блокировок идёт не за год, а за всё время существования аккаунта.
    •      Аномальные голоса: Система блокирует подозрительные голоса (3 попытки, Device ID + пинкод, новые аккаунты менее 7 дней). При попытке голосования с Device ID, уже использованного для другого голоса, система блокирует голос.

## 3. Сверка цифрового отпечатка (Хэш-функция SHA-256)
... Главным инструментом верификации приложения для конечного пользователя является уникальная буквенно-цифровая контрольная сумма (Хэш):
1. После утверждения стабильной версии кода, системе присваивается официальный хэш-код (например, по стандарту `SHA-256`, который выглядит как строка из цифр и латинских букв, например: `e3b0c44298fc1c149afbf4c8996fb92427ae41e46434ca495991b2b855`).
2. Подобный эталонный номер публикуется на GitHub и в независимых каналах верификации.
3. В самом приложении НКП/ЭКА (в # Разделе «О программе») должен быть выведен текущий хэш запущенной сборки. 
**Верификация чистоты кода и сборки**:
    1. После утверждения стабильной версии кода на GitHub генерируется его эталонный криптографический хэш-код (SHA-256).
    2. Для удобства ручной проверки пользователей в интерфейсе приложения (в # Разделе «О программе») и на GitHub отображается сокращённый цифровой отпечаток (первые 10 символов хэша), а также интерактивный QR-код сборки.
    3. Любой пользователь может либо быстро сверить короткие первые символы отпечатка глазами, либо мгновенно проверить подлинность сборки сканированием QR-кода через защищенный модуль приложения.
    4. Полная строка SHA-256 при этом проверяется фоновыми алгоритмами P2P-сети автоматически для исключения любых модификаций исходного кода.

4. Любой пользователь или доверенный ИТ-специалист может сравнить эти две строчки символов. Посимвольное совпадение хэша на GitHub и хэша в запущенном приложении является математическим доказательством того, что код удаления данных не был изменен, и приложение работает строго по регламенту ТЗ.
