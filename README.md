## 1.7  Три режима обработки и хранения информации
- Система поддерживает три  режима хранения и синхронизации данных:
  ### 1. Режим смартфона
Приложение НКП на смартфоне может хранить данные временно, локально в «нулевом состоянии» (когда в сети нет активных ПК-Хранителей). Однако это предусмотрено только для регистрационных процедур и первичной настройки.
Важно: До момента активации первых ПК-Хранителей приложение не выполняет функции голосований, оценок, массовых жалоб, проектов и любых других операций, требующих обработки больших массивов данных.

Причины:
1.	Нагрузка на устройство: Хранение всех данных (голосов, оценок, проектов) на смартфоне создаёт колоссальную нагрузку на его память, процессор и батарею, что делает телефон непригодным для повседневного использования.
2.	Безопасность: Смартфон — это устройство, которое всегда онлайн. Хранение на нём всех шардов сети делает его главной целью для хакеров.
3.	Стабильность сети: Без ПК-Хранителей P2P-сеть не имеет опоры. Голосования, проведённые в таком режиме, не будут защищены от подлога и потери данных.
Система переходит в полноценный рабочий режим только после того, как в сети появляется минимальное количество (7) активных ПК-Хранителей, распределённых по регионам. 

### 2. Режим P2P (ПК-Хранители)
P2P-сеть — это место для хранения любых данных_ распределенное хранилище системы
  В ней хранятся:
•	Голоса, оценки, жалобы.
•	Бланки и аналитические таблицы.
•	Хеши ключей (пинкодов, МК, Т0).
•	Данные пользователей (в зашифрованном виде).
•	Справочники (регионов, должностей).
P2P-сеть — это «облако» без единого сервера. Оно состоит из множества ПК-Хранителей, каждый из которых хранит часть данных (шарды). 
 - Данные хранятся децентрализованно на ПК-Хранителях пользователей.
- Синхронизация через протоколы libp2p и P2P-сеть.
- Основной режим для Этапа 1-2 (до 20 000 пользователей).
- 
### 3. Режим Дата-центров
- Данные хранятся на профессиональных серверах (дата-центрах) при масштабировании
свыше 20 000+ пользователей. 
-   Синхронизация через защищённые каналы.
-  3. Переход между режимами:
- Бесшовный и плавный: Данные не теряются, синхронизация продолжается без 
вмешательства пользователя. Система автоматически определяет, какой режим 
активен, и переключается при необходимости (например, при 
выходе из строя ПК-Хранителей).
-   Криптографическая защита (хеши, МК, TOTP) сохраняется в обоих режимах.
-   
## 1.8 Фиксация времени (Source of Truth).
- Система фиксирует момент начала голосования и далее ведёт отсчёт времени локально. 
- При подключении к сети  производится корректировка времени по узлам синхронизации.
    • «Временем истины (Source of Truth) для всех блокировок и разрешений является 
    системное время ПК-Хранителя,   синхронизированное по NTP.
    • Время на мобильном устройстве пользователя игнорируется и используется 
    исключительно для отображения на экране».
    • Система привязана к локальному времени региона, к которому привязан 
    пользователь и его Хранитель.
    • Для каждого голоса сохраняется неизменяемая временная метка (Timestamp) 
    момента его регистрации, которую 
    невозможно отредактировать задним числом.

## 1.9  Взаимодействие с "Кассой" (Внешний модуль).
- Финансовый модуль "Касса" является отдельным, независимым юридическим и 
программным контуром. "Касса" не имеет  права проводить транзакции без 
подтверждения личности через НКП. НКП выполняет для "Кассы" только функцию 
идентификации и не участвует в движении денежных средств.

## Народная касса
Условие активации:
•	Народная касса становится доступной только после выполнения полного плана размещения ПК-Хранителей (54 точки).
•	До этого момента все финансовые операции заблокированы.
Причина:
•	Без полноценной сети P2P невозможно гарантировать безопасность и прозрачность финансовых транзакций.
•	Касса работает только в устойчивой, децентрализованной сети.

##    Внешние сервисы.
- Передача данных во внешние сервисы (Google Диск, Telegram и др.) возможна 
только по явной команде пользователя для его личных целей. 
Эти сервисы не являются частью архитектуры хранения НКП.

##  2.3  Режимы работы системы и автоматическое управление функциями

1. Статус ПК-Хранителя  
Каждый пользователь добровольно может зарегистрировать свой личный ПК для выполнения функций сервера в своём сегменте-шарде. Этот ПК называется Хранителем.
Хранитель — это не банковский сервер 24/7. Это волонтерский ПК. Он имеет право выключаться тогда, когда удобно его владельцу.

2. Автоматическое управление функциями системы
Система НКП не использует заранее заданные жёсткие правила включения функций (например, «если 54 узла — то всё работает»). Вместо этого система самостоятельно анализирует состояние сети и принимает решения.

Компоненты системы:
1.	Географическая карта — координаты всех плановых точек (54), метка рельефа (горы/равнина).
2.	Проектный список-план — стартовые 54 точки, основа для расчёта нагрузки.
3.	Программа расчёта нагрузки — автоматически определяет, сколько узлов нужно в каждом регионе.
4.	Механизм автоматического управления функциями — система сама решает, какие функции включить.

3. Уведомления и рекомендации
Система отображает на дашборде:
•	Текущий режим для каждого региона.
•	Причины (например: «В вашем регионе недостаточно ПК-Хранителей. Для включения голосования требуется установка узлов в точках: [список]»).
•	Рекомендации по установке новых узлов.

4. Переход между режимами
•	Автоматический, без участия человека.
•	Как только условия меняются — система переключает режим.
•	Решения принимаются алгоритмически, на основе данных. Никакой человек не решает, когда включать голосование. Это делает система.

6. Распределение Хранителей по регионам
Хранители должны быть распределены во всех семи областях Кыргызстана.
Один регион должен иметь резервные ПК-Хранители в количестве 3-х штук.

Система содержит встроенную географическую базу данных, включающую координаты всех плановых точек (областные центры, стратегические сёла, КПП) с указанием:

•	Широты и долготы.
•	Метки рельефа (горы/равнина).
•	Региона и типа точки.
**Количество точек**: 54 (стартовый план).

**Дополнение карты**:

Алгоритм работы:

1.	Сбор данных: Система получает данные из:
o	Географической карты (координаты, рельеф).
o	Проектного плана (54точки).
o	Реального количества ПК-Хранителей в каждом регионе.
o	Нагрузки на каждый узел (трафик, количество пользователей).
2.	Анализ: Система определяет:
o	В каких регионах достаточно узлов.
o	В каких регионах узлов недостаточно.
o	Где нагрузка превышает допустимую.
o	Где географические условия требуют дополнительных узлов.
3.	Решение: Система автоматически выбирает режим работы для каждого региона (или группы регионов):

## 2.5 Режим работы приложения: _Условия  …	Что доступно
1. Только регистрация:  Если нет узлов или нагрузка критическая. Доступна регистрация, настройка ПТ. Хранение локальное на телефоне. Данные не публикуются.
2. Голосование (локальное): Если узлы есть, но нагрузка высокая.  Доступна регистрация + локальные голосования (в пределах региона). Хранение локальное на телефоне. Данные  публикуются в границах данного региона, и не видны другим регионам.
3. Полный режим: Если узлов достаточно, нагрузка сбалансирована.	Доступны все функции (голосования, оценки, проекты, касса, решения ДЛ). Данные  хранятся в сети P2P и  распределяются по шардам. Результаты видны всем: это публичные итоги.

**Детали режима Локального голосования** 
_  Если узлы есть, но нагрузка высокая
•	Доступна регистрация.
•	Доступны локальные голосования — только в пределах данного региона.
•	Данные хранятся локально (в пределах региона).
•	Результаты голосований не публикуются в общую P2P-сеть и не видны пользователям из других регионов.

•	Цель: Обеспечить возможность голосования в регионе даже при отсутствии полноценной сети, но сохранить надёжность работы системы и конфиденциальность результатов до момента перехода в полный режим.

4.	Уведомление: Система отображает на дашборде:
o	Текущий режим для каждого региона.
o	Причины (например: «В вашем регионе недостаточно ПК-Хранителей. Для включения голосования требуется установка узлов в точках: [список]»).
o	Рекомендации по установке новых узлов.
5.	Переход между режимами: Автоматический, без участия человека. Как только условия меняются — система переключает режим.
Важно: Решения принимаются алгоритмически, на основе данных. Никакой человек не решает, когда включать голосование. Это делает система.

Mesh-сеть для нулевого цикла: Используется на этапе активации первых ПК-Хранителей Mesh-сеть используется локально, в пределах одной комнаты или дома (смартфон ↔ ПК). В этом режиме горы не создают препятствий, так как расстояние минимально.

## Связь между узлами P2P сети:

После активации ПК-Хранители взаимодействуют через интернет (сотовая связь, оптоволокно). В этом случае горы могут влиять на качество связи, но только через доступность интернет-инфраструктуры. Сама P2P-сеть работает через интернет и не зависит от рельефа.

Но горы влияют на скорость и стабильность интернет-канала, который используют узлы P2P. Именно поэтому план разместить 48 узлов (особенно в горных районах) — это стратегически верное решение.  Если в отдалённом горном селе интернет пропадёт или будет очень медленным, и там не будет своего ПК-Хранителя, жители не смогут нормально пользоваться системой.

А если у них будет свой узел (тот самый 48-й ПК), то:
1.	Он будет их локальной точкой входа в сеть, что может работать стабильнее, чем если бы они тянулись к узлу в областном центре.
2.	Система становится живучее: даже при сбоях в центральных районах, локальный узел продолжит обслуживать своих пользователей.
Итог:  здесь нет противоречия:
•	Горы не влияют на саму логику работы P2P-протокола через интернет.
•	Но Горы влияют на качество интернет-соединения (скорость, стабильность), через которое P2P работает.
И поэтому  план с 54 узлами направлен на то, чтобы минимизировать именно вторую проблему, делая сеть более устойчивой на всей территории страны.

## Технические средства обеспечения связи в удалённых и горных районах:

Для обеспечения устойчивой работы ПК-Хранителей в местах, где отсутствует или нестабильна проводная интернет-инфраструктура (высокогорные сёла, отдалённые пастбища, приграничные зоны), система предусматривает использование спутникового интернета (Starlink и аналоги). Starlink — это не просто «ещё один провайдер». Это единственный реальный способ связать горные точки в единую сеть без многокилометровых кабелей и вышек сотовой связи.

Преимущества использования Starlink:

•	Работает в любой точке, где есть прямая видимость на небо (горы, степи, отдалённые районы).
•	Не требует прокладки кабелей, строительства вышек или сложной инфраструктуры.
•	Обеспечивает скорость, достаточную для синхронизации P2P-сети и передачи голосов.
•	Уже официально запущен в Кыргызстане (с мая 2026 года) и доступен для физических лиц и организаций.
Рекомендация:

•	В планах размещения узлов предусмотреть возможность подключения через спутниковые каналы для точек, где проводной интернет отсутствует или нестабилен.

 ## 2.0.1 Шардированная архитектура реестра.
- Для обеспечения быстродействия и хранения данных 50+ млн аккаунтов используется шардированная архитектура. Реестр данных сегментирован на независимые шарды. Каждый шард может размещаться на узлах ПК-Хранителях (автономные сервера на ПК) и обслуживает определённый сегмент пользователей. Синхронизация между шардами осуществляется по протоколу P2P/MESH.

## 2.4. Хранение ключей и данных

###  2.4.1 Хранение регистрационных данных 

Для проверки отдельных действий (подпись бланка, вход в систему, восстановление аккаунта) система хранит отдельные хеши каждого типа  регистрационных данных:

•	Хеш пинкода подписи — для подтверждения авторства.
•	Хеш телефонных номеров — для привязки устройств.
•	Хеши всех прочих данных по отдельности при анонимной и открытой регистрации.
•	Мастер-ключ (МК) — это сводный, общий хеш всех данных, используется для общей идентификации личности.

Важно: Из МК невозможно выделить отдельные хеши регистрационных данных.  Каждый хеш вычисляется независимо и хранится отдельно.
- Система использует строгую иерархию хранения ключей и данных. Каждый тип данных хранится на том устройстве, где он  максимально защищён, с соблюдением принципа Air Gap (изоляция критических данных от интернета).

### 2.4.2 Где хранится TOTP ключ= ключ Т0 после синхронизации:
В энергонезависимой памяти модуля часов на ПТ (постоянно). ПТ является единственным постоянным хранилищем Т0. (аппаратно-защищённое хранилище TEE). Здесь ключ хранится постоянно с момента регистрации.
•	
•	На смартфоне Т0 не хранится никогда — только временно, для синхронизации, затем удаляется, затем вычисляется и  хранится только хеш ТО, а исходный ключ удаляется.

1.	На ПК-Хранителе Т0 не хранится. Т0 передаётся на ПК_Хранитель в пользовательском формате: (в виде цифр, например: 563_239_146 ) только для активации модуля часов. После успешной синхронизации и запуска часов Т0 удаляется с ПК. Математические часы на ПК работают автономно, используя только внутреннее текущее время и внутренний алгоритм. Не  хранят точку отсчёта, но хранят хеш ТО. 

### 2.4.3 Где хранится Мастер ключ
Мастер-ключ (МК=хеш мастера ключа) создаётся на основе всех регистрационных данных и передаётся на ПТ в пользовательском формате и хранится там постоянно. 
 На смартфоне МК хранится временно  до момента появления сети P2P (ПК-Хранителей). После успешного переноса эталонного МК в P2P-сеть, его локальная копия на смартфоне затирается.»

-  Запрещено: Хранить TOTP-ключ в постоянной памяти смартфона, в облачных сервисах. «Не рекомендуется: Хранить TOTP-ключ на внешних носителях (флешках, внешних дисках), так как это увеличивает риск утери или кражи. Система автоматически не сохраняет ключ на внешние носители. Если пользователь самостоятельно создаёт копию ключа на флешке, он берёт на себя ответственность за его сохранность.» 

### 2.4.4 Что хранится на смартфоне, на ПК и в сети P2P

1.	На смартфоне временно  хранятся регистрационные данные в виде хешей по отдельности и общего хеша всех регистрационных данных- это  МК в пользовательском формате.
2.	После образования сети P2P( сети из ПК-хранителей_ 7шт.), все данные из смартфона переносятся в сеть.
3.	На смартфоне хранится часовой механизм,  а ключ TOTP=(ключ точки отсчёта) от часового механизма не хранится. Приложение хеширует ключ сразу после установки часов и после установки и хеширования сразу удаляет.
4.	На ПК хранится часовой механизм. На ПК также как и на смартфоне, после установки часов и хеширования ключа ТО, .. ключ ТО удаляется.
5.	На  ПК_Хранителе, после его активации в сети P2P хранятся все и любые данные, связанные с работой приложения. ПК-Хранитель это часть всей P2P сети.
6.	В нулевой точке, когда ещё нет ПК-хранителей функцию P2P сети выполняют сами телефоны, но только для целей регистрации пользователей,  до  момента появления в сети P2P первых семи ПК-Хранителей.  

###  2.5  Принципы передачи и исполнения команд

- 2.5.1 Принцип передачи команд
- 
    • Полное приложение на смартфоне не отправляет команды напрямую на ПТ.

•	(например, показывает мастер-ключ или сообщение об успешном удалении). Данные не передаются обратно на смартфон; 
•	результат видит только пользователь на экране ПТ.
Это гарантирует, что критически важные данные никогда не покидают изолированную среду ПТ.

Мастер-ключ (МК) — это хеш (SHA-256) всех регистрационных данных пользователя, представленный в удобном для ручного ввода формате:
XXXX_XXXX_Слово1_Слово2 (8 цифр + 2 слова).

•	Исходные регистрационные данные кроме псевдонима   не хранятся в системе. Вместо них в системе хранится только эталонный МК.
•	Из МК невозможно восстановить исходные регистрационные данные (псевдоним, номера телефонов, пинкод, отпечатки и т.д.).
Назначение МК:
•	Идентификация личности — подтверждение, что пользователь является владельцем аккаунта.
•	Активация ПК-Хранителя — сверка введённого МК с эталоном в P2P-сети.
МК используется только в этих двух случаях. В остальное время он не задействован в работе системы.

### Правила нумерации позывных ПК-Хранителей:
1.	Нулевая точка (первые Хранители в регионе):
В каждом регионе первые ПК-Хранители получают порядковые номера, начиная с 001.    Пример: Бишкек_К 001, Нарын_К 001, Талас_К 001.
2.	Историческое сохранение:
Первые три позывных в каждом регионе (001, 002, 003) сохраняются навсегда как исторические. Они не подлежат изменению или переприсвоению.
3.	Перерасчёт при масштабировании:
Когда сеть охватывает всю страну и количество Хранителей в каждом регионе превышает 3, система автоматически пересчитывает порядковые номера для всех новых Хранителей, начиная с 004.
4.	Уникальность в рамках региона:
После перерасчёта каждый позывной становится уникальным в пределах своего региона. Например, в Бишкеке не может быть двух Бишкек_К 004.
5.	Механизм перерасчёта:
o	Система фиксирует момент, когда количество Хранителей в регионе достигает 4.
o	Автоматически запускается процедура перенумерации: первые три остаются, все новые получают номера с 004.
o	Перерасчёт происходит без участия пользователя, в фоновом режиме.

 ### Требования к разработке программных модулей для работы с Т0

Для обеспечения работы математических часов и двухэтапной синхронизации устройств программисты должны разработать следующие программные модули:

1.	Модуль генерации ключа Т0 — для приложения на ПТ (проверочном телефоне). Ключ генерируется на основе случайной точки отсчёта (время активации) и пользовательских настроек. Алгоритм — TOTP (RFC 6238) с произвольной Т0. Смартфон не генерирует Т0, а только получает её от ПТ через QR-код и синхронизирует часы.
2.	Модуль генерации QR-кода на ПТ — для проверочного телефона (ПТ). QR-код содержит Т0, настройки генерации и пользовательский вид пинкода. Генерируется после получения данных от смартфона (QR-код-1).
3.	Модуль генерации двух QR-кодов на ПК-Хранителе:
o	QR-код №1 — для передачи на смартфон с целью сверки Мастер-ключа (МК). Генерируется до подключения к P2P-сети. … Решает вопрос сверки МК
o	QR-код №2 — для передачи в P2P-сеть через смартфон. Содержит неполный позывной, номер сессии и хеш Т0. ….. Решает вопрос входа в сеть.
4.	Модуль хеширования Т0 — единый для смартфона и ПК-Хранителя. Обеспечивает вычисление хеша Т0 (SHA-256) для сверки на этапе активации ПК-Хранителя. Хеш Т0 используется для проверки подлинности устройства без передачи самой Т0 по сети.

### 4.  Штатный режим работы ПК  (Дневная сессия).

    • Включение: 09:00 утра по местному времени региона.
    • Отключение: 20:00 вечера по местному времени региона.
    • В 20:00 Хранитель прекращает прием новых транзакций (голосов). Все накопленные данные фиксируются на диске в виде локального снепшота.
    • Владелец ПК вправе выключить компьютер немедленно после 20:00 или через час (по своему усмотрению). Система НЕ ожидает завершения репликации с другими регионами.

### 5. Синхронизация и восстановление (Дельта-синхронизация).

    • Если выключение произошло до завершения репликации, на диске сохраняется флаг sync_pending = true.
    • При включении ПК (в 09:00 или позже) Хранитель проверяет флаг, запрашивает у 2–3 соседей голоса за период отсутствия и применяет данные.
    • Время досинхронизации не должно превышать 15 минут. Если данные не получены, Хранитель запускается с пометкой sync_warning.

### 6. Режим планового отсутствия ПК (Vacation Mode).

Владелец ПК имеет право приостановить участие в сети по уважительным причинам (болезнь, отпуск, командировка). Он фиксирует остановку ПК- Хранителя в бланке: Form № 0.7 – Бланк временного отключения ПК-хранителя
    • Для активации необходимо в интерфейсе указать дату начала и возврата.
    • Система запускает миграцию данных на резервные Хранители (не более 15 минут).
    • После миграции ПК выключается. Статус Хранителя сохраняется. При возврате данные восстанавливаются от соседей.

 ###  Система защиты: что от чего защищает

… Каждый элемент системы защищает свой фронт. Нет одного «супер-ключа», который бы всё решал. Есть система, где каждый слой защищает от своей угрозы.
    • Псевдоним + пинкод + ПТ → защищают вход.
    • МК + хеши → защищают данные от хаккеров
    • ПТ + Device ID+ бумажные записи → защищают от фейков.
    • P2P + хеши+ ПК- Хранители(автономные сервера) → защищают от удаления, просмотра и подделки истории.
Социальный барьер для фейков
Чтобы переломить результаты голосований, надо на каждые 1 млн. пользователей создать или подкупить 500 тыс человек, а в открытых аккаунтах они никогда не пройдут в круг доверенных лиц, т.к. там нужно завоевать доверие в живом формате, в работе с людьми.

6.2 Сбор голосов и хеширование итогов
    • Все голоса собираются в защищённом контейнере в открытом виде (доступном только системе).
    • Защита контейнера обеспечивается кодировщиками (шифрование, изоляция, контроль доступа).
    • Подсчёт голосов происходит напрямую (математика работает с открытыми данными внутри контейнера).

6.3. Хеширование итогов голосования (для архива)
    1. Публикация результатов: После завершения голосования система подсчитывает голоса и отображает итоги в соответствующем бланке: Form № … /итог Этот бланк виден всем пользователям.
    2. Фиксация хеша: После отображения результатов система вычисляет хеш (цифровой отпечаток) заполненного бланка итогов. Хеш включает в себя все данные, отображённые в бланке.
    3. Архивация: Вычисленный хеш сохраняется в архиве (наряду с другими хешами).
    4. Проверка подлинности: Если правительство или любой другой пользователь захочет проверить подлинность результатов, он может нажать кнопку «Проверить». Система заново вычислит хеш текущего бланка и сравнит его с сохранённым хешем.
        ◦ Если хеши совпадают → бланк подлинный, данные не изменены.
        ◦ Хеш результатов служит доказательством целостности итогов голосования
        ◦ Если хеши не совпадают → бланк был изменён (подлог).
        ◦ 
    5. Готовность к новым данным: После отправки  хеша в архив, контейнер (память, где шёл подсчёт) очищается и готов к приёму данных следующего голосования.
    6.  Пустые бланки не хешируются.

6.4   Жизненный цикл бланка в личном кабинете гражданина:
    • После успешной отправки заполненного бланка, данный экземпляр бланка в личном кабинете пользователя получает статус "Архив" и перемещается в # Раздел "История".
    • Одновременно на место использованного бланка система автоматически выдаёт новый, чистый экземпляр бланка того же типа.
    • У пользователя всегда должен быть доступен актуальный бланк для каждого типа действия. Ситуация "бланки закончились" недопустима.
    • Исключение: если бланк сезонный/одноразовый, то после использования он уходит в архив без замены. Список таких бланков согласовывается отдельно.
    • Статус использованных бланков: 
    • После использования бланк становится недействительным для нового голосования, но не удаляется. Он сохраняется в архиве как доказательство голосования.

### 7.1  Голосование по конкретным деяниям 

- Гражданин  фиксирует конкретное действие (или бездействие) госслужащего: например, «министр Иванов 1 марта 2026 года не ответил на обращение №123».
- Для этого он заполняет Form №1.2 (Фиксация нарушений и положительных деяний) или Form №9.1 - Заявления, просьбы и жалобы  от граждан
- К заявке обязательно прикладываются доказательства (ссылки на Google Диск, фото, видео).
- Начинается голосование и после завершения система подсчитывает результаты по единому правилу. 
- Результат: Form № 1.2_B/итог - Результат голосования по зафиксированным нарушениям и положительным деяниям госслужащих  
- Количество подтверждённых фактов – количество нарушений или положительных деяний, - это абсолютное число, не переводится в проценты. Количество фактов не суммируется как голоса, а фиксируется как есть: сколько их, начиная с одного до 30 в месяц.   
-  Количество  нарушений за год (5 → отставка, 10 → прокуратура)
5–9 нарушений за календарный год → система направляет уведомление президенту и в НКП: «Рекомендуется рассмотреть вопрос об отставке».
- 10 и более нарушений за год → система автоматически направляет материалы в Генпрокуратуру.
-  Цикл контроля (30 дней → повторное голосование)
- Если госслужащий не ответил на обоснованную претензию или не исправил нарушение в течение 30 дней, система инициирует повторное голосование по тому же факту.
- Цикл повторяется каждые 30 дней до устранения нарушения.

# Раздел 8  Единое правило подсчёта голосов для всех бланков

- На всех бланках голосования по любому вопросу фиксация ответов происходит по единому правилу:
- 
- По каждому пункту голосования гражданин выбирает один из трёх вариантов (например: «Да», «Нет», «Воздержался»).
- 
- Каждый участник в соответствующей ячейке (на пересечении строки и столбца) ставит единицу (1) в том варианте, который он выбирает.
- Единица — это числовой маркер, который участвует в математических операциях.
- 
- Галочка (✓) не используется,  за исключением одного случая при заполнении формы № 1.1: …  Form № 1.1 — Оценка деятельности Главы государства (по системе Лао Цзы)
- 
- При подведении итогов система автоматически суммирует все единицы по каждой строке (пункту голосования) и по каждому варианту («Да», «Нет», «Воздержался» и другим вариантам  положительных или отрицательных ответов).
- Доля каждого варианта вычисляется по формуле:
- 
- Доля варианта = (Количество единиц по варианту / Общее количество единиц по строке) × 100%
- 
- Результат округляется до одного десятичного знака (например, 45.6%).
- Сумма долей по трём вариантам всегда равна 100%.
- 
- Формула универсальна и не зависит от названий вариантов ответа («Да/Нет/Воздержался», «Подтверждаю/Не подтверждаю/Воздержался», «Одобряю/Не одобряю/Воздержался» и т.д.).

# Раздел 9  Защита приложения и данных

### Защита результатов голосований

### 9.1. Порядок проверки учета голоса гражданина

1.	Квитанция гражданина.
... После каждого голосования система выдает гражданину в Личный кабинет электронную квитанцию. Квитанция содержит персональный хеш-код голоса. Квитанция сохраняется в разделе "История" в виде QR-кода.
... Персональный хеш-код голоса (Hash) вычисляется как: SHA-256( Псевдоним + Пинкод подписи + Время голосования по времени ПК-Хранителя  + Номер бланка + Выбранный вариант голосования ). Это гарантирует, что хеш уникален для каждого голоса и не может быть переиспользован или подделан.

2.  Публичная доска хешей.
... Все хеши голосов, принятые с 09:00 до 20:00, ежедневно публикуются в разделе аналитических таблиц (Form-.../итог) в виде обезличенного списка по регионам. Список публикуется в виде таблицы с колонками: Регион | Хеш-код голоса | Время голосования по времени ПК-Хранителя.  

3. Проверка.
...Гражданин, если пожелает,  вводит номер своего хеш-кода из квитанции в поисковое поле. Система открывает список хешей его региона, где он голосовал и автоматически прокручивает таблицу к строке с этим хешем, выделяя её (например, подсветкой или рамкой). Гражданин находит в этом списке свой хеш-код. Наличие хеша в списке является доказательством учета голоса.
Такой подход делает систему не просто «честной», а зримо честной. Пользователь не просто получает ответ — он видит доказательство своими глазами.

4. Защита от подлога.
Ежедневно в 20:00 по времени ПК-Хранителя для всего массива хешей региона вычисляется итоговый контрольный код (Merkle-Root). Итоговый контрольный код публикуется в системе. Любое изменение, добавление или удаление хотя бы одного хеша приводит к изменению итогового контрольного кода. Сверка по контрольному коду является математической гарантией целостности данных.
9.2  Защита от квантовых компьютерных атак и взлома сети
Принцип: Система НКП спроектирована таким образом, что даже квантовый компьютер не может взломать механизм генерации кодов. Это достигается не за счёт сложности алгоритма, а за счёт отсутствия предсказуемой точки отсчёта.

**Система НКП не имеет единой точки входа для атак**:

1.	 Перехват трафика. Все данные передаются в зашифрованном виде. Ключи расшифровки не хранятся в сети, поэтому перехваченные данные невозможно расшифровать.
2.	Подмена данных. Каждый голос, жалоба или оценка подписываются пинкодом и TOTP-кодом. Подмена данных требует знания Т0 (точки отсчёта), которая неизвестна злоумышленнику и не хранится в системе.
3.	 Атака на P2P-сеть. Данные распределены по независимым узлам (ПК-Хранителям). Отключение одного узла не нарушает работу сети, так как данные дублируются на других узлах.
4.	Взлом смартфона. На смартфоне не хранятся ни Т0, ни Мастер-ключ. Даже при полном взломе смартфона злоумышленник не получит доступа к критическим данным системы.
5.	Система НКП не зависит от алгоритмов, которые могут быть взломаны квантовыми компьютерами:
6.	Не используется RSA, ECC или другие алгоритмы с факторизацией.
7.	Используется случайная Т0, которая не может быть вычислена.
8.	Криптографическая стойкость основана не на сложности алгоритма, а на непредсказуемости источника.
Итог: Система НКП останется безопасной даже при появлении квантовых компьютеров, способных взламывать современные алгоритмы шифрования.

#### 1. Распределённое хранилище (P2P)

•	Требование: Система не имеет центрального сервера. Все данные (голоса, оценки, жалобы, предложения, проекты) хранятся в децентрализованной P2P-сети на ПК-Хранителях. Это обеспечивает невозможность блокировки или удаления данных властями.

 Функциональные требования

•	Подключение к сети: Приложение подключается к P2P-сети при её наличии (после активации 7 ПК-Хранителей). До этого данные хранятся локально на смартфоне.
•	**Система полностью открывает все функции только при условии  входа в полный режим: Если узлов достаточно, нагрузка сбалансирована.	** Доступны все функции (голосования, оценки, проекты, касса, решения ДЛ). Данные  хранятся в сети P2P и  распределяются по шардам. Результаты видны всем: это публичные итоги.  ( смотрите раздел 2, пункт 2.5: Режим работы приложения)

	Синхронизация в реальном времени: Новые голоса, жалобы, предложения распространяются по сети в реальном времени (задержка — секунды, а не часы).
•	«Догоняющая синхронизация» (catch-up sync): Если ПК-Хранитель был выключен несколько дней, при включении он должен быстро (за 1–2 минуты) получить все изменения, произошедшие в его отсутствие, и восстановить актуальное состояние.
•	Выборочная загрузка данных: Данные не транслируются «всем подряд». Система запрашивает только то, что нужно пользователю в данный момент (по ID, по поиску, по теме).
•	Автоматическое удаление старых данных: Старые жалобы и предложения автоматически удаляются из сети по истечении срока (TTL): жалобы — 1 год, предложения — 2 года, возмущения — 6 месяцев. Итоговые результаты голосований хранятся постоянно.
•	Работа без интернета (локальный режим): При отсутствии интернета приложение сохраняет голоса и данные локально.  (до появления сети). При восстановлении соединения данные синхронизируются в фоне, без потерь. Все локально сохранённые данные автоматически отправляются в сеть, синхронизируются и занимают своё место.

### 	Восстановление ПК-Хранителя после бездействия:

Если ПК-Хранитель был выключен длительное время (несколько дней, недель или месяц), при включении он должен:

1.	Быстро восстановить актуальное состояние — получить все изменения, произошедшие в его отсутствие (дельта-синхронизация).
2.	Время восстановления — не более 2–3 минут (в зависимости от объёма изменений).
•	Перераспределение нагрузки при бездействии:

Если ПК-Хранитель не отвечает более 12 часов (в период голосований) или 24 часов (в обычный период), система автоматически перераспределяет его шарды на другие активные ПК-Хранители.
При возвращении ПК-Хранителя в сеть, нагрузка перераспределяется обратно (или остаётся на новых узлах, если они уже взяли её на себя).

•	Защита от внешнего вмешательства: Никакой внешний администратор не может удалить или изменить данные в сети.

#### 11.1. Принцип коллективного суверенного узла (Защита от поштучной регистрации иностранцев)

• Иностранное государство подключается к системе только как целостная Национальная Курултайная Платформа конкретной страны (например, НКП России, НКП Китая, НКП Франции, НКП США и т.д.).

• Эти три доверенных лица несут полную персональную и коллективную ответственность за легитимность информации, передаваемой от лица их государства.

12.4. Безопасность и защита данных

    • Air Gap: Критические операции (подпись, генерация ключей) выполняются только на ПТ (устройство без интернета). ПТ не имеет доступа к интернету. Все критически важные данные передаются через QR-коды или ручной ввод.
    •      P2P-сеть: Все данные (голоса, оценки, проекты) хранятся децентрализованно на ПК-Хранителях. Отсутствует центральный сервер. Данные синхронизируются через libp2p.
    •      TOTP-ключ хранится только на ПТ. На смартфоне и ПК ключ не хранится. При проверке ключ на смартфоне и ПК отсутствует. Все операции с ключом выполняются через ПТ.

    •      Логирование: Все события (голосования, блокировки, изменения бланков) фиксируются в неизменяемом журнале. Логи невозможно изменить или удалить. Хранятся не менее 5 лет.

    •      Уровень 2: После 3-х предупреждений аккаунт блокируется на год. Система фиксирует 3 нарушения и автоматически блокирует аккаунт.

- Код, отвечающий за работу внутренней камеры на этапе регистрации, обязан содержать сквозную команду полной перезаписи и уничтожения временных файлов фотографий паспорта и бумажной копии сразу после успешной генерации анонимного Токена гражданства. 
- Если в коде будут обнаружены скрытые функции логирования, дублирования или сетевой отправки исходных изображений, сборка признается скомпрометированной.

#### 2. Контроль целостности через Воспроизводимые сборки (Reproducible Builds)
- Чтобы исключить риск подмены честного кода с GitHub на шпионскую версию при публикации в Google Play / App Store или при прямой установке APK-файла, проект НКП/ЭКА обязуется использовать стандарт воспроизводимых сборок. 
- Любой сторонний программист должен иметь возможность скомпилировать приложение из данного открытого исходного кода на своем оборудовании и получить идентичный бинарный файл.

## 3. Сверка цифрового отпечатка (Хэш-функция SHA-256)
... Главным инструментом верификации приложения для конечного пользователя является уникальная буквенно-цифровая контрольная сумма (Хэш):
1. После утверждения стабильной версии кода, системе присваивается официальный хэш-код (например, по стандарту `SHA-256`, который выглядит как строка из цифр и латинских букв, например: `e3b0c44298fc1c149afbf4c8996fb92427ae41e46434ca495991b2b855`).
2. Подобный эталонный номер публикуется на GitHub и в независимых каналах верификации.
3. В самом приложении НКП/ЭКА (в # Разделе «О программе») должен быть выведен текущий хэш запущенной сборки. 
   
**Верификация чистоты кода и сборки**:

    1. После утверждения стабильной версии кода на GitHub генерируется его эталонный криптографический хэш-код (SHA-256).
    2. Для удобства ручной проверки пользователей в интерфейсе приложения (в # Разделе «О программе») и на GitHub отображается сокращённый цифровой отпечаток (первые 10 символов хэша), а также интерактивный QR-код сборки.
    3. Любой пользователь может либо быстро сверить короткие первые символы отпечатка глазами, либо мгновенно проверить подлинность сборки сканированием QR-кода через защищенный модуль приложения.
    4. Полная строка SHA-256 при этом проверяется фоновыми алгоритмами P2P-сети автоматически для исключения любых модификаций исходного кода.

1. Любой пользователь или доверенный ИТ-специалист может сравнить эти две строчки символов. Посимвольное совпадение хэша на GitHub и хэша в запущенном приложении является математическим доказательством того, что код удаления данных не был изменен, и приложение работает строго по регламенту ТЗ.
